# Agent Note: 智能模式自动路由策略改进计划

Status: proposed

日期：2026-09-13  
代码基线：`f3bd0014e629bf6ef716a8c2577c20b78eb7d24e`（0.4.1）  
范围：智能模式的路由预算、候选选择时机、交付阶段调度、平局与反馈、触发覆盖率及成本评测。  
交付类型：设计与实施计划；本次不修改运行代码或默认配置。

## Problem

前一轮主要修复了验收回读、证据边界、宿主接线、去重和预算上限等实现缺陷。它们的回归通过，不能证明 smart 的触发时机、覆盖范围和成本收益已经合适。本计划承接[上游对照计划](2026-09-13-upstream-routing-tools-review-plan.md)，重点改进策略，不重新列出已经关闭的缺陷。

当前基线有五个需要处理的设计问题：

| 方向 | 当前事实或证据 | 要改善的行为 |
| --- | --- | --- |
| 路由额度 | 默认每任务 2 次，计划预审、语义分类和实际评分分别占用。离线复现：计划预审 1 次＋分类 1 次后，compare 无法预约，此时仅用了 2 次模型调用；分类＋compare 后也没有 track 尝试额度 | 一次语义分类及其后续评分成为一个路由周期，模型调用仍分别计量 |
| 选择时机 | 自动 compare/select 主要在 `agent/turn-stopping` 执行 | 受信候选就绪后，在下一步模型生成前提供选择结果 |
| 交付阶段 | 结构化 track 优先于普通最终验收；`preferFinal` 通常要先购买一次达标 track 才设置 | 已进入交付阶段时直接验收，省去不改变下一步行动的进度评分 |
| 决策反馈 | select 自动反馈使用 ranking/index 指定候选，缺少明确的并列说明和稳定来源定位 | 明确唯一优胜、并列、相同候选和证据不足；反馈能定位到对象 |
| 策略评测 | 只读分析可同时没有语义线索与最终验收资格；0.9 是分类器自报置信度；失败成本及真实标签评测仍不完整 | 用实际任务标签评价触发、误放行、重复调用和额外成本 |

对应实现：[config.ts](../../../../src/config.ts) 156–170、[router.ts](../../../../src/router.ts) 的 `reserve/semanticRouteHint`、[index.ts](../../../../src/index.ts) 的停止钩子、[auto.ts](../../../../src/auto.ts) 的 `analyzeAutoTask`。

最近一次发布门禁在该基线上通过：354 项测试通过、2 项 Python parity 测试因缺少同级仓库跳过，`lib/` 重建无差异。这是此前复核结果；本次文档编写不重复运行测试，也没有真实模型评测。

## Decision

### 1. 目标与边界

本轮选定以下五项工作：

| 编号 | 优先级 | 目标 | 交付判据 |
| --- | --- | --- | --- |
| S01 | P1 | 合并分类与执行的路由尝试 | 默认额度能执行“计划预审 → 分类＋compare”，并保留最终验收 |
| S02 | P1 | 将受信候选选择前移 | 候选评审结果出现在下一步主模型请求之前，同一候选不在停止边界重复评分 |
| S03 | P1 | 交付阶段直接最终验收 | 指定交付场景省去 track；最终阈值和失败处理不变 |
| S04 | P2 | 明示平局并提供可定位反馈 | 并列不被描述成明确优胜，来源和失败判据可定位 |
| S05 | P1/P2 | 补齐测量并校准覆盖率 | 先补必要成本/路由记录，再完成有真实标签的分层评测 |

S02、S03 的新调度首先用于 smart。manual 保持显式调用；strict 的失败阻断、独立最终验收和有限预算退出规则保持原有约束。S01 作为共享计数规则同时覆盖 smart/strict，变更的计数单位须在两种模式中明确说明。

保留的硬约束：

- 最终通过仍使用 `sessionAccepted`：胜者为 A、均分达标、逐项达标；不因 Todo 完成或选择完成而直接放行。
- 路由和最终验收的尝试额度继续独立；任务/会话模型预算以及最终验收预留继续生效。
- 解析失败、非法引用、取消和过期结果不得记为成功；每次自动反馈都由已消费的周期或既有一次性耗尽通知覆盖。
- 不自动触发 `verifier_best_of_n`，不把所有模型请求改为多候选生成；其基线比较继续不可省略。
- 保留现有 PPT、评分标尺、相同候选语义、默认判据、温度和评分通道探测。近似平局策略和阈值调整要等 S05。
- 所有新增证据、消息、引用都脱敏并限长；复用 `itemBudget()`、确定性分隔块和真实渲染计量。
- 保留现有工具和导出接口；首轮优先复用配置，不为每个阶段增加新开关。

### 2. S01：一个分类与执行周期只消耗一次路由尝试

#### 计数契约

将“最多路由次数”的单位明确为**路由周期**。一次周期可以直接执行结构化决策，也可以先分类、再执行该分类选择的一个决策。

默认单裁判、三条判据、候选互异且评分正常时：

| 周期 | 路由尝试消耗 | 无缓存、无重试时的模型调用 |
| --- | --- | --- |
| 结构化 compare | 1 | 6（自动 compare 两轮） |
| 语义分类 → compare | 1 | 1＋6 |
| 语义分类 → 三候选 select | 1 | 1＋9（自动 select 一轮） |
| 语义分类 → none / 低置信 | 1 | 1 |
| 语义分类解析失败或非法引用 | 1 | 已发生的分类调用；按模式处理失败 |
| 结构化 track | 1 | 3 |
| 计划预审 / 单个 Team 任务闸 | 各 1 | 各自原有调用 |
| 最终验收 | 不占路由尝试；占最终验收尝试 | 6 |

这些数字是明确条件下的逻辑调用数，不包括重试、能力探测、缓存命中或附加裁判。判据数和裁判数变化时使用实际值重新计算。首轮保持现有逻辑调用预约口径，不能把它宣传为传输请求总数的硬上限；插件重试、通道降级及不可见的宿主内部尝试在 S05-A 中分别说明。

默认 2 次不是保证每个阶段都能各跑一次。计划预审加一次候选周期后，track 仍可能没有额度；此时应按已有资格进入最终验收，而不是增加无限的阶段预算。

#### 实现安排

1. 分类预约成立时立即消费一次任务/会话路由尝试，并为分类请求预留调用额度。
2. 分类期间保持该预约的 in-flight 所有权。得到合法且足够可信的路由后，在**同一预约**上提升到 compare/select/track，并补充该阶段的调用预留。
3. 提升预约必须原子检查当前任务、快照、取消状态、实际评分配置和最终验收预留。不能先 commit 分类释放锁，再通过第二次 reserve 抢执行额度。
4. none、低置信、非法引用、失败、取消均结束当前周期；不退回已消费的尝试。执行预算不足时记录“分类成功、评分未执行”，不能伪装成 none 或已评审。
5. 周期执行成功后才 commit 实际对象的 fingerprint；分类 none 的完成记录与真正评审完成的记录分开。
6. 分类去重以当前任务、可见证据和分类配置为依据；仅增加一条没有新证据的叙述，不应再次付费分类。失败重试仍受周期上限约束。
7. 保留保守的模型额度预留，首轮不按缓存命中自动返还。实际请求统计另由 S05-A 记录；不将预算余额等同于已发生费用。

在 `AutoVerifierRouter` 上扩展预约延续/提升能力即可，不引入通用事务框架。现有 `reserve/commit/fail` 接口保持可用，停止钩子改用同一周期完成分类与执行。

主要文件：`router.ts`、`index.ts`、对应测试；`client-i18n.ts`、README 和 AGENTS.md 同步计数单位。UI 成本说明区分“一次周期的代表性成本”与“任务硬上限”，不要把单轮示例当作整个任务的最坏开销。

#### 验收

- 默认 2 次额度下，计划预审后仍可执行一次“分类＋compare”；分类＋compare 后仍可申请第二个 track 周期。
- none 与失败也消费一个周期；反复停止不能产生无限分类。
- 同一 agent 并发预约、取消、任务更换、分类后证据变化，不会重复消费或错误 commit。
- 提升后所需额度加最终预留恰好等于上限时通过，超出 1 次时拒绝；任务与会话两层均覆盖。
- 原“90 次路线＋12 次最终验收超过 96”继续被拒绝；最终额度不被挪用。
- 用注册的停止钩子检验完整路径，不只断言 router 内部计数。

### 3. S02：受信候选在下一步模型生成前评审

#### 借鉴点与宿主可行性

TurboAgent 在将所选回复交给客户端前完成筛选，进而影响接下来的行动。本项目借鉴这个介入顺序，保留 DSH 原生工具与证据边界。[TurboAgent 请求管线](https://github.com/llm-as-a-verifier/TurboAgent/blob/31ea8dadc00211b96544d3edd02ded1ef64e9856/turbo_agent/proxy/backend.py)

本次已核对：

- npm 锁定的 `@deepseek-ai/dsh-agent@0.1.1-rc.2` 声明了 `agent/pre-step`，可通过 waterfall 返回 `{kind:'enter', messages}` 或保留 reject。
- 本地 DSH `2377c272a8e839e0a84c9f0e623b867a1dce2014` 在上一 step 完成后、下一次模型请求前 await 该钩子；自带模型切换提示也通过返回的 messages 注入当前步骤。
- Workflow 脚本公开的编排 API 没有通用 verifier 工具调用函数；文档示例不能虚构 `verifier_select()` 为脚本内置 API。

核对位置：安装包 `lib/types/runtime-types.d.ts:47–52,235–241`；同级 DSH `packages/core/agent-loop/src/agent.ts:240–258,284–319`、`packages/core/agent/src/model-selection.ts:108–118`。

#### 选定方案

新增受限的 `agent/pre-step` 入口，首轮只处理**已完成、版本正确、同组的 Workflow 候选 envelope**：

1. 仅在 smart、插件开启、符合子会话策略、没有新的直接用户/团队任务需要接管时尝试。
2. 尊重 `await next()` 的 reject、取消和宿主主动清空消息的决定。不能借注入提示重新唤醒被宿主拒绝或取消的步骤。正常工具后续步的 messages 可以为空，不能一概据此跳过；首步被清空、或原有 offered continuation 被下游清空时才按宿主 admission 规则保持跳过，参考上述 model-selection 实现。
3. 从已经记录的上一阶段结果识别未处理的 compare/select；不在此运行语义分类，也不做 track、最终验收或候选生成。
4. 使用 S01 的预约、证据边界及同一评分实现；评审结果通过返回的 `messages` 交给**当前步骤**，不通过 `agent.steer()` 延迟到下一步。
5. 唯一胜者、平局及相同候选的反馈按 S04；成功评审继续设置最终验收要求。候选选择不证明实施已完成。
6. pre-step 与 turn-stopping 共用对象指纹和 in-flight 状态，保证同一份候选只评分一次。只抽取两入口必需的共享评分/反馈小段，不重写整个 `index.ts`。
7. 无可用预算或评分失败时，smart 保留原有继续工作的行为并记录原因；停止边界仍负责兜底。不能声称所有候选都已在实施前评审。
8. 评审期间任务、配置或证据失效时，丢弃结果、不注入过期胜者。自己的 verifier 请求不得递归触发该入口。

停止钩子保留：它仍能处理没有后续 step、普通 Subagent 语义线索及其它未处理对象。显式工具的描述和 README 同步强调“先获得真实候选，再比较，随后实施”，并提供符合实际 Workflow API 的候选产出示例。

主要文件：`index.ts`、`router.ts`、`index.test.ts`、README。无需改宿主，也不拦截每个 `llm.stream` 请求。

#### 验收

- 事件顺序必须为：Workflow 完成 → 判官评分 → 选择消息进入下一主模型请求 → 主 Agent 生成实施操作。
- 之后的停止边界不重复购买同组评分；显式先评审过的同组也不重复。
- 新用户任务、团队新任务、取消、宿主 reject、宿主清空 continuation、晚到的子 Agent 结果均有定点回归。
- 不把同一个工具批次中已经开始的并行操作描述成被提前阻止；该入口控制的是下一 step。
- 裸 Subagent 报告、失败 Workflow、截断或无效 envelope 不触发早评审；它们仍按原路径处理。
- 两条宿主线分别检验签名和消息交付形状，尤其不能只在不记录消息的假 `steer` 上断言成功。
- 相同候选输入的评分调用数不因两个入口增加。若提前看到的是不同证据快照，明确记录快照差异，不假定其分数应与事后评分相同。

### 4. S03：交付阶段直接进入最终验收

TurboAgent 将额外进度监测作为不影响所选回复的后台观测。本项目借鉴“进度观察与交付判断分工”，首轮只优化调度，不新增后台评分服务或完整在线 ProgressTracker。[进度监测实现](https://github.com/llm-as-a-verifier/TurboAgent/blob/31ea8dadc00211b96544d3edd02ded1ef64e9856/turbo_agent/proxy/backend.py#L272)

#### 调度顺序

smart 的停止边界按以下顺序处理：

1. 当前且有效的显式验收凭据。
2. 既有 Team 任务闸和不能跳过的处理。
3. 尚未评审的候选选择。
4. 符合交付阶段条件时，直接最终验收。
5. 其余情况保持结构化/语义进度路由和普通最终验收资格判断。

交付阶段首版采用窄条件：

- 本任务有非空 Todo 列表，当前条目全部完成；或现有 `preferFinal` 已成立。
- 使用 Todo 快路径时，还应有本任务内可定位的验证运行证据，并满足现有最终验收资格或强制验收要求。
- 没有未处理候选需要先做选择，也没有正在执行的评审。
- 完成信号和验证证据未被同一次失败最终验收消费；相同证据不能反复触发快路径。

Todo 完成仅决定“送去最终验收”，不决定是否通过。验证运行的真实成败都传给最终判官；不把工具调用成功当成测试通过，更不凭 Todo 状态略过错误输出。没有证据或仍有未完成项时保持原路径。

在同一停止边界直接执行 `verifySession`，不先发一条“准备验收”的 steering 再等下一边界。失败后恢复修复/进度流程；只有新实质工作或新的验证结果才能重新激活已经消费过的完成信号。

主要文件：`router.ts`、`auto.ts`、`index.ts` 及对应测试。复用已有证据判据、`verificationEvidence` 和 `preferFinal`，不要复制第二份工具名单或测试签名。

#### 验收

- 无缓存、无重试、单裁判、三判据的完成场景：原 track 3 次＋final 6 次变为只运行 final 6 次。
- 有失败验证输出时，判官仍看到失败；不因为跳过 track 就接受任务。
- Todo 已完成但无验证证据、Todo 重开、新候选出现、判官超时、取消、证据改变，都保持相应正常路径。
- 最终失败后仅复述完成，不再次购买相同快路径，也不能静默获得通过状态。
- 不能为了省 track 合并两套尝试计数或改变最终验收阈值、判据和重复轮次。
- 同时记录主 Agent 续步次数和额外 token；“省 3 次判官调用”不应被未计量的额外主模型步骤抵消。

### 5. S04：平局、相同候选与反馈定位

#### 自动反馈语义

不改变公开工具现有的 `index/ranking/scores/winner` 返回语义。在自动反馈层根据真实结果区分：

| 结果 | 自动反馈要求 |
| --- | --- |
| 唯一最高分 | 给出候选标签、组/候选标识或事件位置，要求实施后验证 |
| 最高分并列 | 列出并列集合，说明没有唯一优胜依据；不能把稳定排序第一项称为明确赢家 |
| identical / identical-candidates | 说明内容相同、未发生质量评分；不继续购买相同候选比较 |
| 未执行 / 预算不足 / 调用失败 | 说明评审没有完成，不能展示为选择成功 |
| 最终验收不通过 | 给出未达标判据和可定位的真实证据；没有定位依据时如实说明缺少证据 |

完全平局沿用当前数值等价口径，不新增随意的“近似平局阈值”。对近似平局增加评分轮数、增加裁判或采用不同模型，均留到 S05 的标注评测后再决定。

反馈首轮采用确定性格式，不新增解释模型调用。已有 compare 判据分数可直接展示；select 没有绝对质量或逐项解释时，只报告相对排序。不得编造失败文件、行号或验证命令；决策快照仍只供观察，不能反向读入判定流程。

新增定位信息和摘要纳入消息预算，总自动反馈上限 4000 字符，固定文案也计入；逐项分摊。过长标识用事件 seq/候选序号定位并说明省略，不将完整候选复制进反馈。所有内容先脱敏。

若后续需要对显式工具新增“并列集合”等字段，另行同步 output schema、真实返回值校验和文案；本轮不是该新增字段的前置依赖。

主要文件：`index.ts`、`auto.ts`、`statistics.ts`、`client-i18n.ts` 及定点测试。选择分数、验收分数与分类置信度继续分开表达。

#### 验收

- 全部平局和部分最高分并列都不产生“候选 0 明确最好”的反馈。
- 完全相同候选保持 0 次判官调用；后续最终验收仍可识别没有工作。
- 组中标签重复、长 ID、中文标签、多判官分歧时，反馈仍能定位对象且不超过上限。
- 失败的具体判据在反馈中可见；无证据时不生成虚假的行动依据。
- 反馈变化不新增模型请求、不改变 engine 排名或判据阈值。

### 6. S05：先补可观测成本，再评测触发与覆盖率

本项接续旧计划 F07 的实际消费统计和 F09 的效果评测；两者不能在代码批次结束时提前标为完成。

#### S05-A：必要的测量记录（与 S01 一起落地）

在现有统计记录中增量保存路由周期与阶段信息，至少能关联：

- 周期 ID、任务起点、触发点（pre-step/turn-stopping/plan/team）、对象 fingerprint、最终去向与跳过原因。
- 尝试次数、保守预留调用数、真实发生的评分调用、插件可观测的请求尝试与重试。
- 缓存命中、通道 fallback、取消、部分失败和已知 token 使用量。
- 分类完成但执行未发生、提前选择已执行、跳过 track 直接验收、最终未验收退出。
- 原始条目数、保留/省略数、实际证据字符数，供识别因限长造成的路由变化。

“周期”“评分调用”“传输尝试”是不同单位。诊断行可以保留，但不得把多条诊断行当成多次模型调用。请求在返回 usage 前失败时标记用量不完整；宿主内部不可见重试和失败 token 不能推算为已知 0。

不在首轮实现预算自动退款。预算继续保守，统计反映真实可观测消费；重试或缓存不能让另一个并发预约透支。旧统计文件继续读取，`success` 继续表示调用是否抛错，最终是否验收由 verdict 表达。

使用现有 `record`、usage 与 trace 通路补齐失败/取消的累计信息，不新建计费平台。新增字段尽量可选，必要的 UI 解释同步中英字典；涉及工具返回的 stats 字段时同步五工具 schema。

主要文件：`caller.ts`、必要的 `top-logprobs.ts`、`index.ts`、`statistics.ts`、`replay.ts`、`client-i18n.ts`。只传递与当前调用有关的观测信息。

验收：用假模型覆盖成功、首次失败后重试成功、全部失败、缓存命中、通道降级、请求前取消及请求后取消；已知请求不丢失，未知 usage 不被显示成完整零成本。真实事件计数与周期汇总可核对。

#### S05-B：有真实标签的策略评测

首批约 30 个脱敏样本用于发现问题，分层覆盖：

1. 代码修改与验证。
2. 只读检索/研究结论。
3. 写作和文本交付。
4. 同题候选、不同子任务和候选平局。
5. Todo 长任务、Team 转交及计划预审。
6. 纯对话、取消、失败和应当免检的场景。

样本可交叉覆盖，但主类别和标签标准预先固定。任务标签至少包括：应否复核、应调用的工具/阶段、哪些结果是同题替代候选、真实交付是否满足要求。标注依据产物与执行证据，不能先看裁判分数再给标签。

评测分两层：

| 层次 | 做法 | 能回答的问题 |
| --- | --- | --- |
| 离线调度回放 | 固定事件与 scripted 分类/判官结果，重放当前和新策略 | 状态机、计数、重复购买、时机、限长及关闭路径是否正确 |
| 真实模型对比 | 固定模型、判据、通道和任务；对照 manual、当前 smart、新 smart，strict 作辅助参照 | 触发是否合适、选择和最终验收是否有收益、成本与延迟是否可接受 |

同一份历史轨迹无法证明“更早给反馈”会怎样改变后续实施。S02 的效果需另做实际运行对照；不能把离线重排事件当成在线收益证据。提前评审也不能看到其时点之后的证据。

报告至少包含：

- 路由精度与漏检：应复核任务中的命中、漏检，以及不应复核任务中的误触发。
- 最终误放行、误阻断、未验收退出和错误的候选归组。
- 相同证据重复评分次数、分类无执行比例、选择介入实施之前的比例。
- 每任务与每个有效决策的额外判官调用、主 Agent 续步、已知 token、P50/P95 延迟；缺失用量单列。
- 明显优劣与难分候选分别统计；explicit-tag 与 top-logprobs 分开报告，裁判降级也单列。
- 每项样本数、错误案例和不确定性。30 个样本不能证明低误放行率。

触发覆盖率先回放、再小样本实际对比，首版不直接把 research/writing 预设绑定为“所有只读任务都自动验收”。若出现重复可解释的漏检，再针对任务类型提出窄触发规则；纯对话继续免检。0.65、0.684、0.9 和各重复轮数在证据不足时保持原值。

真实评测需要选定数据与明确调用预算；日常单元测试始终使用假 fetch/stream，不发真实请求。S05-B 的完成条件是有可核对的标注与对比报告，不是只有一个评测脚本。

### 7. 实施批次、依赖与回退

| 批次 | 工作 | 依赖 | 交付物 |
| --- | --- | --- | --- |
| A | S01＋S05-A 必需记录 | 无 | 同周期预算、失败/用量标记、真实钩子回归、计数说明 |
| B | S04＋S03 | A | 可定位反馈、并列说明、交付直验收及节省调用的回归 |

| D | S05-B | A–C 的可观测实现 | 固定样本、离线回放和真实对比报告、是否调整触发/阈值的结论 |

每批保持独立提交和 implemented Agent Note。提交前 `pnpm run verify:release`，涉及源码必须同步 `lib/`；不在本计划阶段改版本或发布。

回退粒度按批次：

- S02 收益不足或出现宿主交付问题时，撤回早入口，保留原停止兜底。
- S03 快路径有误调度时，恢复 track 原优先级；不改变最终通过规则。
- S01 出现计数或锁问题时独立回退，不能靠增加默认额度掩盖。
- S05 的标签、观测与失败用量事实保留；不能因回退策略而删除不利结果。

不增加一组长期实验开关。先在固定测试与受控实际样本中验证，再决定作为 smart 默认行为交付。

### 8. 跨批次验收清单

- 同一个对象在早入口、停止入口及显式工具路径之间只购买必要的评审；没有新证据不反复分类或 steering。
- 当前任务、快照、预约所有权和取消状态均有效后才交付结果；新用户/团队消息不会收到旧任务的胜者。
- 最终验收没有被 Todo、平局、相同候选、诊断成功或分类高置信代替。
- 所有不可执行的路由都能区分预算、重复、失败、非法引用或未满足触发条件；不存在“没评分却显示通过”。
- 真实返回值过工具 schema；新增可选统计字段兼容旧记录，两份 i18n 字典同步。
- 预算测试包含恰好相等、超出 1 次、任务/会话两层，以及同周期分类提升后的边界。
- 证据测试保留 300 条长会话、最新失败、PTC、长候选去重和 1130/1131/1132 分隔边界。
- 测试要检查实际渲染文本和下一次主模型请求的内容；不能只断言内部 `evidenceChars` 或 `steering.length > 0`。
- 不把新增测试数量作为效果完成标准。代码验收、宿主接线验收、真实效果评测分别报告。

## Alternatives considered

1. **直接提高默认路由次数。** 不采用。它不能修正分类与执行重复占用一次决策额度的问题，也会扩大最坏成本；先明确周期单位和真实消费。
2. **为分类、候选选择、进度、计划和团队各加一组额度。** 首轮不采用。配置和调度复杂度过高；一个受限路由周期加独立最终验收更符合当前范围。
3. **完全照搬 TurboAgent 的全请求代理。** 不采用。它会改变 DSH 的模型接入和工具执行成本；本轮只借鉴先选择后行动、进度观察与验收分工。
4. **在任意工具完成后做语义评审，或在每个写入工具前拦截。** 不采用。会增加调用并与并行工具执行交错；已确认的 pre-step 入口更适合把结果交给下一次行动规划。
5. **仅修改工具描述，让 Agent 自己记得提前调用。** 作为示例和指引保留，但不作为 S02 的自动化交付。其完成标准必须包含真实钩子的消息顺序。
6. **Todo 全部完成就直接放行。** 不采用。Todo 是阶段信号，实际通过只能由原最终验收规则决定。
7. **平局时自动增加裁判或套用固定 gap 阈值。** 暂缓。缺少当前模型/通道下的标签证据；先如实反馈并列，保持既有评分语义。
8. **现在全面扩大只读任务触发，或先改默认阈值。** 暂缓。先用 S05 识别具体漏检和误触发，再提交窄范围变更。
9. **重写路由器、独立计费服务或新建 DAG 看板。** 不采用。现有模块足以承载这些改进，优先局部扩展并验证连接处。

## Consequences

本计划把“实现缺陷已修复”之后的策略工作拆成五项可验收交付。预算编排、交付阶段调度和平局反馈有现有代码依据，可以先实施；早评审使用已经确认的宿主入口，但收益仍需实际运行验证；触发覆盖和阈值调整由真实标签评测决定。

旧计划 F07 的实际消费统计由 S05-A 接续，F09 的评测由 S05-B 接续。相关代码、记录和报告未全部交付前，两项继续保持未完成；本计划也保持 proposed，不因代码测试通过提前标记整体完成。
