# Agent Note: 适配 DSH 0.1.7 volatile Config 表单投影与热更新

Status: implemented

## Problem

在 DSH 0.1.7-alpha.1 宿主环境中，用户在 Web UI 打开「LLM Verifier」设置页面时报错失败，界面提示：“未注册 Verifier 设置命名空间，请重启 DSH 宿主。”

经比对 DSH 宿主提交 `601d6761e4`（`feat(settings): project volatile Config through profile-backed forms (#4587)`）定位根因：
1. **宿主 API 破坏性移除**：DSH 0.1.7 彻底删除了 `ctx.settings.installSection` 与 `ctx.settings.register` 方法。旧版 `installVerifierSettings` 在 0.1.7 宿主上因缺少分支而静默空转，未能建立任何设置源绑定与更新监听。
2. **表单投影依赖 volatile 标记**：0.1.7 的 `SettingsForms.describe()` 直接从 Loader Entries 的 `Config` schema 提取表单（`volatileForm(schema)`）。若插件 schema 及其子字段均未声明 `volatile`，`volatileForm` 返回 `undefined`，`describe()` 会直接跳过该 Entry。
3. **命名空间缺失**：由于上述过滤，前端 RPC `remote.settings.describe()` 返回的 `namespaces` 中不包含 `ns === 'llm-verifier'`，`src/client.tsx` 的 `load()` 校验抛出 `settings.nsUnregistered` 错误。

后续用户反馈进一步暴露**两个并存故障**：设置页能加载但点「保存设置」后数值立刻回弹默认值，且插件在运行时读不到用户写入的值。仅设置 `meta.volatile` 只能修复第 2、3 条（表单投影），无法修复保存链路：

4. **社区 schemastery 不产生 volatile 引用**：插件在 `dependencies` 中编译期解析到社区 `schemastery@3.18.0`，该实现**没有** `.volatile()`，且其 `Schema.resolve` 不含任何 volatile 分支。因此 `markVolatile` 的 `meta.volatile = true` 回退分支只写了元数据，`Config['~standard'].validate()` 返回的仍是**普通对象**：实测 `isVolatile(value) === false`、`volatileEntries(value).length === 0`。
5. **宿主的 volatile-only 快路径因此吞掉整次保存**：Loader 的 `Entry.update` 用 `equalExceptVolatile`（只看 schema 元数据）判定「仅 volatile 字段变化」，进入 `_commitVolatile()`；该函数对 `fiber.config` 做 `volatileEntries` 收集，得到 **0 个引用**后直接 `return true`。于是配置被当作「已提交」丢弃，既不走 `internal/update` 重启流程，也没有任何引用被更新，`ctx.fiber.config` 永远停在启动值——UI 重新载入即显示默认值，插件也读不到新值。

## Decision

1. **Schema 级 volatile 声明 + 本地实现 cosmokit 引用协议（双环境兼容）**：
   - 实现 `markVolatile(schema)`：schema 已是 volatile 时原样返回（宿主 `.volatile()` 二次调用会抛 `volatile schema is already wrapped`）；否则优先调用 `.volatile()`，在社区版 `schemastery` 下回退到 `.extra('volatile', true)` 并确保 `meta.volatile = true`；最后统一叠加引用协议。
   - 实现 `installVolatileRefProtocol(schema)`：在**实例上**用 `Object.defineProperty` 遮蔽 `~standard`（不动社区 prototype），把 `validate()` 的成功结果包成 `createVolatileConfigRef()` 产出的 volatile 引用；`issues`（校验失败）原样透传，Fail Closed 语义不变。以 `WeakSet` 保证幂等。
   - 实现 `createVolatileConfigRef(value)` 与 `isVolatileConfigRef(value)`：按 cosmokit 的公开协议复刻——引用是冻结对象，暴露 `get()`，写句柄挂在 `Symbol.for('cosmokit.volatile.write')` 且不可枚举；快照按 cosmokit 规则递归深冻结（拒绝函数、环、类实例）。同一份协议同时被宿主 ESM 与插件 CJS 通过 `Symbol.for` 跨副本识别。
   - `export const Config = markVolatile(z.object({ ... }))` 将整个配置 Schema 声明为 volatile，使 DSH 0.1.7 `volatileForm` 将全部字段投影入设置表单，且 `isVolatilePath` 允许任意路径编辑；同时 `validate()` 产出根级引用（`volatileEntries` → `[{ path: [] }]`），让 Loader 的 `_commitVolatile()` 真正有引用可写。
2. **Volatile 引用透明解包**：
   - 增加 `unwrapVolatileConfig(value)`：递归解包由 `@deepseek-ai/cosmokit` 生成的 `Volatile` 引用（`{ get(): T }`）。
   - `resolveConfig(config)` 开头首先执行 `config = unwrapVolatileConfig(config)`，保证即使 DSH 0.1.7 宿主传入 `Volatile<Config>`，内部各逻辑也能透明读取纯对象，同时不破坏旧宿主或单测直接传普通对象的分支。
3. **适配 0.1.7 设置生命周期与热更新**：
   - 在 `installVerifierSettings` 中保留原有的 `installSection` 与 `register` 分支以确保 0.1.1~0.1.6 兼容；
   - 增加 0.1.7+ 回退分支：
     - 若 `sctx.settings.configure` 存在，调用 `sctx.settings.configure({ auto: false }, ctx.fiber)` 关闭冗余的通用自生成表单，防止界面重复；
     - 配置源动态读取 `unwrapVolatileConfig(ctx.fiber?.config ?? entry)`；
     - 监听宿主 `loader/volatile-update` 事件，当用户在设置页面保存修改后自动触发 `onChange`，刷新并发限制器并作废旧处理意图。

## Alternatives considered

- **为 Config 每个字段逐项添加 `.volatile()`**：
  - 缺点：`Config` 包含数十个字段（含 `autoProcessSelection` 的复杂 transform 与嵌套数组），如果子字段内出现非法嵌套 volatile 会被 `@deepseek-ai/schemastery` 的 `validateVolatileSchema` 拒绝报错；且社区版 schemastery 类型声明不支持 `.volatile()` 链式调用，需要大量类型断言。
  - 结论：将根 Schema 标记为 volatile 是宿主官方支持并测试覆盖的标准用法（见 `configuration.spec.ts:143`），既能一次性开放所有字段编辑，又保持 schema 简洁。
- **只设置 `meta.volatile`（本轮已交付后被证伪的中间态）**：
  - 缺点：社区 `schemastery` 不产出引用，只能修好表单投影，保存链路完全失效（见 Problem 4、5）。
  - 结论：否决。`meta.volatile` 是投影的**必要非充分**条件；必须同时满足引用协议。
- **将 dependencies 中的 `schemastery` 切换为 `@deepseek-ai/schemastery`**：
  - 优点：该实现自带 `.volatile()`，无需本地协议代码。
  - 缺点：`@deepseek-ai/schemastery` 是宿主 vendor 包，仅在宿主发布/链接它的环境可解析；插件同时支持 0.1.1~0.1.6 宿主线与外部 npm 发布生态，直接改换依赖会让未 linkage 场景解析失败。此外 `src/config.ts` 也被打进**浏览器设置页 bundle**，不能依赖任何仅 Node 可解析的包。
  - 结论：否决，改为在本地复刻 cosmokit 的公开引用协议；`markVolatile` 仍先探测 `.volatile()`，因此宿主自带实现时行为完全一致。

## Consequences

- 运行在 DSH 0.1.7-alpha.1 宿主中时，`remote.settings.describe()` 正常输出 `ns: 'llm-verifier'` 的设置描述符，Web 界面顺利加载配置，不再报“未注册命名空间”错误。
- `Config['~standard'].validate(raw)` 返回根级 volatile 引用：`isVolatileConfigRef(value) === true`、快照深冻结、写句柄不可枚举。保存时 Loader 的 `_commitVolatile()` 能收集到 1 个引用（`path: []`），通过 `updateVolatile` 把新快照写进**运行中 fiber 持有的同一个引用对象**，再发 `loader/volatile-update` 触发 `onChange()` 刷新并发限制器并作废旧处理意图——保存生效且无需重启宿主。
- 插件侧配置源 `unwrapVolatileConfig(ctx.fiber.config ?? entry)` 因此始终读到最新快照，工具调用（含 `verifier_current_session` 等）使用的是用户保存后的值。
- `~standard` 遮蔽只发生在 `~standard` 读取路径；0.1.1~0.1.6 旧宿主走可调用 schema（`schema(value)` → `Schema.resolve`）与 `installSection` / `register` 分支，看不到该遮蔽，兼容路径保持不变。
- 快照是深冻结的，`resolveConfig` 只能读不能原地改；`unwrapVolatileConfig` 仍在该函数首行解包。
