# Agent Note: 离线回放 —— 阈值扫描与解析器 drift 检测

Status: implemented

## Problem

「验收阈值该调到哪里」和「提示词或解析器改动有没有回归」这两件事，此前只能靠重新跑真实验收来回答：贵、慢、不可重复。
而决策快照已经存下了门控看过的全部信息与判官原始回答——不利用它们等于白存。

## Decision

1. `replay.ts`（纯函数）+ `lib/replay.js` 导出 + `scripts/eval-replay.mjs` CLI：
   - **阈值扫描**：从 `statistics-v1.json` 的 `verifier_current_session` 记录重放**当前生效的 `sessionAccepted` 规则**，
     在每个阈值上重新判定，并区分「均分不够」「逐项不达标」「输给基线」「无法解析」四种落选原因；
   - **解析器回放**：从 `decisions-v1.json` 重放每次调用保存的原始回答，用当前解析器重新解析并报告 drift——
     提示词或解析逻辑的回归在**没有模型调用**的情况下暴露。
2. 快照按内容选标签（`<score_A>` / 最后一个 `<cN>` 且方向相反 / 既无标签也不该打分 → `not-scored`），
   不假设所有回答都是 `score_A`。
3. `top-logprobs` 通道的分数是 token 分布上的期望，而快照不保存分布，因此其文本通道重解析出现 drift 属预期，
   脚本在输出里明示这一点。

## Alternatives considered

1. **用真实模型重跑验收来对比阈值**：否决。贵、慢，且每次结果都不同，做不了回归。
2. **把回放做进看板（前端计算）**：否决。回放要读全量记录并跑纯函数，放进 CLI 才能复现、才能进发版自查。
3. **只回放分数、不回放解析器**：否决。解析器 drift 是最容易悄悄回归的一类（提示词一改，标签形状就可能变）。
4. **把 drift 当失败、以非零码退出**：本次未做。`top-logprobs` 的文本重解析必然 drift，把退出码做成红色会淹没真正的回归。

## Consequences

- 阈值调参从「跑一次真实验收」变成「读本地 JSON」；解析器回归零成本可查。
- 首次回放（本机真实数据）：3 个话题、17 次调用、14 次门控验收；0.5–0.9 全部阈值下 14 次全通过（判官对每次会话都给 1.00），
  解析器 15/15 match、0 drift。结论是「最该修的不是阈值，而是判官的区分能力」，这把判别探针从「待做」变成了「有工具可做」。
- 回放依赖快照的确定性，因此 `decisions.ts` 的写入顺序与上限必须确定（标签排序 + 按调用数平分窗口）。
