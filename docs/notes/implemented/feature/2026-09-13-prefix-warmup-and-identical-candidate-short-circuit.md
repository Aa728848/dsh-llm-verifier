# Agent Note: 每个不同提示词前缀只预热一次，并短路逐字节相同的候选

Status: implemented

## Problem

三件事：

1. `compare` 把（判据 × 轮次）个调用**同时**发车，谁都命中不了前缀缓存：成对提示词的头（任务 + 两条轨迹 + 评分标尺）
   是共享的、只有判据在尾部，但没有先行调用把公共前缀写进后端缓存。
2. 逐字节相同的候选仍然送给判官：既浪费调用，又可能拿到「自信的分数」，让会话验收放行一个与空工作基线无法区分的会话。
3. 前缀缓存有没有生效只能靠猜——统计里没有这个指标。

## Decision

1. **按不同提示词前缀分组，各预热一个 job**：`compare` 按 A/B 槽位（奇偶轮次换位）分组，每组先跑一个 job 再扇出其余；
   `track` 先跑第一轮再扇出其余重复轮次。**调用次数不变**，只改变顺序（多一次串行等待）。
2. **逐字节相同的候选不送判官**：`compare` 两侧相同 → `identical: true` + `tie` + 0.5/0.5（不是高分）；`select` 全同 →
   0 调用、全 0.5；有重复则先去重再跑锦标赛，结果按代表性索引映射回原列表（`rankByScore`）；空白候选直接报错。
   verdict 分别记 `identical` / `identical-candidates`，看板据此区别于「真的判过且打平」。
3. **前缀缓存命中率进统计**：`statistics.ts` 的 `prefixCacheHitRate` + 看板一栏 + 两份 i18n。
4. `core.ts` 的 `buildPairwisePrompt` 写明「判据必须留在尾部」的约束（上游 `build_prompt` 同样如此），
   否则顺序看起来随意、很容易被改坏。

## Alternatives considered

1. **串行发全部调用**：否决。等价于放弃并发，且仍然没有显式预热。
2. **为预热额外发一次调用**：否决。预热必须用本来就要发生的调用，否则等于加价。
3. **对相同候选直接给高分**：否决（红线）。会让会话验收放行与空工作基线无法区分的会话。
4. **照搬上游「多数票直接返回未评判候选」**：否决。它把未评判的结果当结论；本项目只采纳其「跳过锦标赛」的成本收益，
   语义保持在 `identical` 标记 + 0.5 平局。
5. **只在看板展示命中率、不进统计**：否决。指标要能被聚合与回放，不只是当次展示。

## Consequences

- 输入成本显著下降（公共前缀由后端缓存服务）；**调用次数逐位不变**，`engine.test.ts` 用「顺序改变、调用次数不变」的断言锁死。
- 相同候选不再消耗调用，也不会被误判为「更好」；看板能区分 `identical` 与真的打平。
- 预热分组成为显式约定：改分组必须同步改测试。
