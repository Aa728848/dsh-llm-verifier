# Agent Note: 建立 DSH 版本升级维护技能，并明确它与 Agent Notes 的分工

Status: implemented

## Problem

本仓库同时声明支持多条 DSH 宿主版本线（0.1.1–0.1.7），因此"宿主更新了，插件跟着改"是一条**会反复走**的维护路线。但这条路线此前只有知识、没有入口：

1. **流程知识散在提交历史与 Agent Notes 里**。0.1.6 与 0.1.7 两次对齐各自留下了笔记，但"下次该从哪一步开始、用什么命令找出宿主改了什么"没有任何单一入口；每次升级都要重新发现一遍。
2. **本机的 harness 位置是一条隐性前提**。`tsconfig.local.json` 约定 `../deepseek-harness`，而本机 harness 在 `C:\Users\A\Documents\deepseek-harness`（不在仓库同级）；同时它是**本地开发 checkout**，与 npm 发布物的关系需要每次确认。这条前提此前只散落在两份 process 笔记的正文里。
3. **陷阱是跨版本重复的**。`paths` 失败静默回退 `node_modules`（假绿）、`as any` 藏住宿主面、npm 上已删除的包仍能解析成功（死导入潜伏五个版本线）、客户端 external 模块具名导入在旧宿主是 `undefined`（React 抛错导致整页白屏）、测试跑在旧宿主类型上——这些在 0.1.6 与 0.1.7 两轮里**各踩了一次**，下一轮还会再踩。

## Decision

1. **新增维护技能 `.agents/skills/dsh-version-upgrade/SKILL.md`**，作为这条维护路线的唯一入口，内容为：本机 harness 路径与版本确认方法、本插件消费的宿主面清单（包 / 服务名 / 事件）、十步升级流程、跨版本陷阱清单、`typecheck:local` 的接通办法、**每次升级的要点索引**（append-only，最新在上）、以及"已知待决"。
2. **发现机制照抄 DSH 生态的既有约定**：技能实体放 `.agents/skills/<name>/SKILL.md`，仓库根再用一个 17 字节的指针文件 `.claude/skills`（内容 `../.agents/skills`）指向它——与 harness 仓库自身的做法逐字节一致（`od -c` 复核过，无尾随换行）。
3. **明确三个落点的一事一主（One home per fact）分工**，并写进技能与 `AGENTS.md`：
   - **SKILL**：怎么做（命令、流程、陷阱）＋每次升级的**要点索引**（一行一句，链向笔记）。
   - **Agent Notes**（`.agents/notes/implemented/`）：为什么这么选、放弃了什么（决策理由与备选方案）。
   - **`AGENTS.md` 第 7 节**：看到哪些代码**不要动**（既定事实与硬约束）。
   - 三者互不复制，只互相链接。
4. **`AGENTS.md` 两处接线**：仓库结构表新增 `.agents/skills/` 行并写明指针机制；第 7 节开头加一句"升级宿主版本线之前先读该 SKILL"，把入口放在未来会话最可能落到的位置。

## Alternatives considered

1. **每个版本一个独立 SKILL（`dsh-upgrade-0.1.8`、`dsh-upgrade-0.1.9`…）**：否决。技能列表会随版本线无限膨胀，且版本之间真正稳定的只有**流程与陷阱**（重复度最高），按版本切分等于把最该复用的部分复制 N 份。要点用索引条目承载，天然可追加。
2. **只写 Agent Note，不建 SKILL**：否决。Note 承载的是**决策理由**，且按治理规则必须写成交付态客观事实、不保留计划态；把可执行流程塞进 Note 会同时污染两边的体裁，并且没有任何机制在"下次升级"时把 Note 推到会话面前。
3. **只写进 `README.md`**：否决。README 面向**使用者**（安装、配置、能力），维护流程与其读者不同；且 README 无自动进入上下文的机制。
4. **把要点索引改成"新升级时新建一份 Note，技能里只留链接"**：部分采纳——做法就是如此（索引条目 → Note）。不同之处在于**索引本身留在技能里**：否则想看清"历次升级分别动了什么"就得逐个打开笔记。
5. **不建 `.claude/skills` 指针，只放 `.agents/skills/`**：否决。指针是 harness 仓库里已验证可用的形态，而本机没有 `~/.claude/skills` 之类的用户级目录可供对照；两种可能的发现路径（原生读 `.agents/skills` 或经指针）都覆盖到，成本是 17 字节。
6. **把技能里的陷阱写成"请自行判断"的抽象原则**：否决。这些陷阱的价值恰恰在于**具体**（哪个命令会假绿、哪个包在 npm 上没了、React 为什么抛错），抽象化后等于没写。

## Consequences

- 下一次宿主更新时，"从哪开始、怎么找破坏性变更、验到什么程度算完、哪些坑不能再踩"有了单一入口；本机 harness 的实际路径不再需要重新摸索。
- 每次升级的收尾动作多了一步：在第 5 节追加一条要点索引（流程第 10 步已写明）。这是有意的最小维护成本，避免索引腐化。
- 技能与笔记存在**有意的重复边界**：技能里出现"0.1.7 删除了 `tool-result` 块"这类事实陈述，是为了让流程可执行；**决策理由与被否决方案仍只有笔记一个归宿**，两者冲突时以笔记为准。
- 已知限制：`.claude/skills` 指针的实际生效路径未经独立验证（本机无其它项目级技能可对照）。即便发现机制不生效，`SKILL.md` 作为仓库内文件仍可被直接读取，符合"提供读取"的要求。
