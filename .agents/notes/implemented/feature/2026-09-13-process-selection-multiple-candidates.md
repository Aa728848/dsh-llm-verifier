# Agent Note: 过程选优支持 3–4 个候选（锦标赛 + 去重短路）

Status: implemented

## Problem

P06 一直固定 N=2：原回复加一份备选，只判一对。上游 TurboAgent 的默认是每个后端模型各出若干候选再跑锦标赛，候选空间更大，也就更能容忍「两份都平庸」的情形；而我们的判别力实测显示难分候选对的中位分差只有 0.018（低于单档步长 1/19），单对很容易退化成 0.5/0.5/0.5 全平——那时这次周期除了绝对分以外没有信息量。

但直接把 N 提到 3 不是免费的：`select` 的对局数涨到 5 对（ring 3 + pivot 2），判官调用约为单对的 5 倍，一个周期就能吃掉任务预算的约三分之一。因此它必须是**可配置、默认关闭（默认 2）**的实验臂，而且必须有短路机制，否则最难分的一堆候选恰好是烧钱最多的情形。

## Decision

配置 `autoProcessCandidates`（整数 2–4，默认 2；越界在 `resolveConfig` 直接报错，因为这里同时是花费上限）：

- **N=2**：完全走原来的成对路径（`buildProcessView` + `deps.compare`），逐位不变；
- **N>2**：生成 N-1 份备选，视图改用新增的 `buildProcessSelectView()`（与成对视图共用抽出来的 `buildProcessContext()` 与 `renderCandidateList()`：任务/约束/证据分节逻辑一份定义，候选预算按**候选数**用 `itemBudget()` 分摊，动作仍是原子单位，总量按渲染文本实测），判定走 `deps.select` → `engine.select` 锦标赛，胜者索引映射回 `[原回复, 备选 1, …]`，`index > 0` 时回放对应的原始块；
- **`deps.select` 是可选接缝**：配了 N>2 却没有它时退回单对并 `warn`，因为缺一个宿主接缝不该中断请求；`settings.candidates` 也是可选的（缺省 2），旧设置生产者不会让周期崩掉；
- **预约用引擎自己的估算器**：`expected = (N-1) + estimateRoutedCalls({kind:'select',…}) × 裁判数`，对局数与 `engine.select` 实际跑的同源，避免第二个会漂移的公式；
- **短路只做一种**：全部候选都与原回复逐字节相同 → 0 次判官调用、`identical-candidate`、回放原回复。部分重复交给 `engine.select` 自己做去重并把分数/排名映射回调用方列表（`rankByScore`），**仍然不采纳**上游「多数票直接返回未评判候选」的语义——那个语义会放行一份从未被评判的候选；
- 统计行沿用同一形状，只有 `toolName` 变成 `verifier_select`（`index.ts` 的 `record()` 按 `report.select` 是否存在选择总结器与工具名），phase/route/预算口径不变；`ProcessCycleReport.select` 与 `report()` 的转发同步补齐（少一处转发会让字段静默消失，`report()` 里已按两个分支展开）。

验证基线：`pnpm run typecheck` 与全量测试通过（585 条，+4）：`process-selection.test.ts` 覆盖「3 候选 → 2 次生成 + 锦标赛 + 胜者索引 2 回放第二份」，覆盖「全部相同 → 0 次 select 调用、回放原回复」，覆盖「缺接缝 → 告警并退回单对」；`config.test.ts` 覆盖默认 2 与 1/5/2.5 的拒绝；`index.test.ts` 端到端断言 3 候选时生成 2 次、判官 6 次（两份相同的备选被引擎去重成一对）、`route.generatedCalls = 2`、`toolName = verifier_select`。

## Alternatives considered

1. **把默认值直接改成 3。** 不采用。5 对 × 3 判据 × 2 轮＝30 次判官调用，约占任务预算三分之一；在难分候选上还常常全平。默认 2、显式选择 3–4 才是诚实的默认。
2. **沿用成对视图给锦标赛用（只渲染前两个候选）。** 不采用。那会让第 3 个候选在没有任何证据的情况下被判官排位，属于静默的错评；视图与候选数必须同构。
3. **复制一份 N 候选的视图构造逻辑。** 不采用。分节预算、约束拒绝、动作原子这些边界是最贵也最容易漂移的部分（见 P06 的视图修正记录），只有一份定义才守得住。
4. **采纳上游的多数票短路（多数一致就直接返回该候选）。** 不采用，与既有设计一致：那等于把一份**从未被评判**的候选交给宿主，而我们的短路只允许「无可判之处」（全部逐字节相同）这一种。
5. **让 `deps.select` 成为必需项并在缺失时拒绝周期。** 不采用。宿主接缝缺失是插件装配问题，不该让一次已经买到生成的主请求失去回放路径；退回单对并告警是有损但安全的降级。
6. **把候选数上限做到 6。** 暂不采用。6 候选的 ring+pivot 对局数与预算下限已经超出默认任务预算的安全区间，真要做必须先解决「多数/近似候选短路」的更强版本。

## Consequences

- 候选空间第一次可调，且默认行为逐位不变（N=2 的回归全部保留）。
- 花费与判据调用随 N 上升是**显式**的：配置范围、README 行、帮助文案与预约估算都写明了对局数量级；统计行的 `toolName` 区分了两种判定通道，离线分臂读数可以直接按它过滤。
- `report()` 的参数与转发必须与 `ProcessCycleReport` 同步——新增字段时漏一处转发不会报错，只会静默丢掉（这次 `select` 就踩到了，已由测试锁住）。
- 更强的多数短路（近似候选、动作序列一致）与 N>4 都留给数据：P05 要回答的仍然是「过程选优整体值不值」，而不是「N 该多大」。
