# Agent Note: 对齐 DSH 0.1.7（生产者自报来源、工具结果独立消息、客户端槽位提供者、设置命名空间读取）

Status: implemented

## Problem

本机 harness checkout 更新到 `dsh-v0.1.7-alpha.1`（npm 上同一版本的 `alpha` dist-tag 已发布）。把 `devDependencies` 升上去后，`tsc --noEmit -p tsconfig.build.json` 一次报出 35 处错误，集中在三处**判定地基**与一处客户端面：

1. **工具结果不再是内容块**。`packages/llm/llm/src/types.ts` 在 0.1.7 删除了 `ContentBlockMap['tool-result']`（`ToolResultBlock` 整个类型消失），同时 `message.ts` 把 `ToolResultMessage` 从"`role: 'user'` + `content: [ToolResultBlock]`"改成"`role: 'tool'` + `content: ContentBlock[]` + 消息级 `isError` + `toolCallId`"。也就是说：0.1.6 及以前，一条工具结果的外层是块、真正输出套在 `block.content` 里、失败标志在块上；0.1.7 反过来——消息本身就是结果，失败标志在消息上。本插件读这一层的地方全中：`session.ts` 的 `textOf()`、`router.ts` 的 `blockText()` / `narrativeText()` / `successful()`、`auto.ts` 的两处子 Agent 结算判定。
2. **`MessageSourceMap` 删除了统一包装**。原本 `{ kind: 'plugin', plugin: '<名称>' }` 覆盖所有插件，0.1.7 改为"each producer declares its own `kind` in its own module; there is no shared catch-all `plugin` kind"。更硬的一层在持久化：`packages/session/session-format-v3-to-v4/src/message-sources.ts` 的 V4 准入接受任何**非空** kind，但**显式拒绝字面量 `'plugin'`**；也就是说继续发射旧包装不是"多一个未知 kind"，而是**写不进去**。宿主侧决策记录是 harness 自己的 `.agents/notes/implemented/architecture/2026-09-09-producer-owned-message-sources.md`。
3. **客户端 `ctx.slots` 的声明包早已换人**。插件 `src/client.tsx` 从 `@deepseek-ai/dsh-client-runtime/client` 导入 `ClientContext`，而该包在 0.1.2 之前就被删除（harness 提交 `be531688f3`，"migrate consumers and remove Runtime"）；`ctx.slots` 现在由 `packages/client/ui-renderer/src/client/index.ts` 对 cordis `Context` 的声明合并提供。这一条是**旧债**：这个导入在 npm 上一直靠 `latest` 标签的 `0.1.1-rc.2` 解析成功，于是 `ctx` 一直是被 0.1.1 类型描述的，0.1.2–0.1.6 期间从没被真正检查过。
4. **客户端图标在 0.1.7 整体改名**。`packages/client/ui-primitives/src/icons/index.tsx` 把尺寸后缀换成笔画后缀（`IconDataOutline16` → `IconDataOutlineRegular`）；逐 tag 核对：`dsh-v0.1.1-rc.2` 与 `dsh-v0.1.6-alpha.2` **只有** `…16`，`dsh-v0.1.7-alpha.1` **只有** `…Regular`。

5. **设置服务删除了按命名空间读取的 `get()`**。0.1.1–0.1.6 的 `SettingsProvider` 有 `get<ns>(ns)`，插件 `top-logprobs.ts` 正是靠它读 `llm-deepseek` / `llm-pi-ai` 的配置来解析直连 logprobs 通道。0.1.7 把整个注册式接缝换成 `SettingsForms`，其原型上**只有 `configure` / `describe`**（`SettingsProvider` / `SettingsScope` / `settingsNamespace` 三个导出一起消失）。因此 `settings.get(ns)` 在 0.1.7 上抛 `settings.get is not a function`，而该异常发生在 `resolveTopLogprobRoute` 内、又不在 `TopLogprobsUnsupportedError` 的捕获范围内，会一路穿透 `callAutomatic` 让整次验收崩溃——这正是用户反馈的"工具验收也是异常的，无法读取设置"。

第 4 条还顺带逼出一个仓库级取舍：图标是普通具名导入，**一份源码无法同时满足两套名字**，所以 `tsconfig.build.json` 的 `typecheck` 门禁不可能既锁最低基线又验通客户端面——这直接反转了 `implemented/process/2026-09-17-local-harness-typecheck-fallthrough.md` 中"devDependencies 有意锁最低版本"的既定决策。

## Decision

1. **工具结果的两侧形态收口到两个函数**：`session.ts` 新增 `toolResultBlocks(block)`（取出旧宿主嵌套块的内层内容，非包装块返回 `undefined`）与 `toolResultFailed(message)`（0.1.7 读消息级 `isError`，更早读块级 `isError`）。`router.ts` 与 `auto.ts` 全部改为调用它们，不再有任何调用点自己写 `block.type === 'tool-result'` 或 `block.isError`。
2. **插件自报来源 kind**：新增 `src/message-source.ts`，以 `declare module '@deepseek-ai/dsh-llm'` 声明 `'llm-verifier': { kind: 'llm-verifier' } & ContextFormed`，14 处注入点统一改用 `kind: 'llm-verifier'`（`form` / `summary` 保持不变）。**不采用**宿主迁移层给未知插件起的 `plugin:<名称>` 名字——那是读旧日志时的改写结果，不是新写入该用的身份。
3. **客户端面改挂正确的声明包**：`import type { Context as ClientContext } from '@deepseek-ai/cordis'`，并补 `import type {} from '@deepseek-ai/dsh-client-ui-renderer/client'`；`dsh.client.inject` 里已被删除的 `@deepseek-ai/dsh-client-runtime` 换成 `@deepseek-ai/dsh-client-ui-renderer`。`ModelProviderGroup` 不再从 `@deepseek-ai/dsh-api-remotes/client` 转出，改为按本页真正读取的四个字段在 `client.tsx` 内声明 `ModelProviderGroupView`（该文件的 `VerifierRemote` 本来就把 RPC 响应结构写在本地）。
4. **图标改为运行时按名探测**：`client.tsx` 顶部从 `dsh-client-ui-primitives` 取模块命名空间，按 `…Regular ?? …16 ?? (() => null)` 解析。图标模块对客户端 bundle 是 external，具名导入在另一侧宿主上就是 `undefined`，而 React 遇到 `undefined` 作为组件类型会**抛错**，会让整个设置页白屏而不是少一个字形。
5. **`devDependencies` 上移到 `0.1.7-alpha.1`，反转旧 pin 决策**：见下方 Alternatives 与跨链的 process 笔记。
6. **顺带修正侧栏 guide 条目缺 `id`**：`SidebarRightGuideEntry.id` 是必填字段，宿主用它做单元格 key 并作为 `entryId` 传给 owner；原实现只有一个匿名条目，运行时不炸但 `entryId` 会是 `undefined`。
7. **设置命名空间读取改为两代接缝探测**：`top-logprobs.ts` 新增 `settingsNamespace(ctx, ns)` 作为这一差异的唯一读取点——先探测 `settings.get` 走 0.1.1–0.1.6 的注册式接缝；否则走 0.1.7 `describe()` 里 `ns` 匹配的那条描述符的 `value`（与宿主 `llm-deepseek` 自己的读取方式一致）。整个函数包在 `try/catch` 里并返回 `undefined`：读不到命名空间只意味着当前路由没有直连 logprobs 通道，据此降级到显式标签通道，**绝不允许设置读取的异常穿透到验收流程**。

## Alternatives considered

1. **把 `{ kind: 'plugin', plugin: 'dsh-llm-verifier' }` 用类型断言继续发下去**：否决。0.1.7 的 V4 持久化准入直接拒绝该字面量，断言只是把编译期错误推成运行时写失败——正是"Fail Closed"要避免的形态，而且它掩盖了一个真实协议变更。
2. **采用迁移层生成的 `plugin:dsh-llm-verifier`**：否决。`producerKind()` 对未知插件名加 `plugin:` 前缀，是**读取历史 V3 日志**时的改名结果；已迁移并自报 kind 的插件再自称 `plugin:*`，等于把自己标成"未声明来源的遗留生产者"，且同一插件在同一份日志里会出现两个身份。
3. **退回 `kind: 'user'`**：否决。`session.ts` 与 `router.ts` 正是用 `source.kind === 'user'` 认任务陈述的，退回后插件自己注入的 steer 文本会被当成用户任务，任务边界与验收区间全错。
4. **客户端图标继续具名导入、放弃旧宿主**：否决。代价不成比例——为了让三种装饰性字形少写 3 行，就换掉 0.1.2–0.1.6 全部宿主的设置页渲染（React 遇 `undefined` 组件类型抛错 → 整页白屏）。
5. **客户端自带内联 SVG 图标，彻底不碰宿主图标集**：否决。那样图标不再跟随宿主图标集的笔画与色值规范，且把一次版本对齐变成为三种字形永久维护一套自有资产；运行时装探针已经把兼容成本压到最小。
6. **`devDependencies` 继续锁 `0.1.1-rc.2`**（旧 note 的既定选择）：否决（本轮）。旧决策的理由是"锁最低基线以持续验证旧宿主可用，新宿主交给 `typecheck:local`"，在**服务端面**依然成立，但客户端面的图标名让它在实现上不可满足：一份源码配不出两套图标名，门禁锁哪一侧就只能验那一侧。而 `typecheck:local` 在本机因 harness 不在约定路径而不可用，等于客户端面完全无人验证。故本轮把 pin 移到 `0.1.7-alpha.1`，宿主面的旧形态兼容改由运行时读取（第 1、2 条）与回归测试承担。
7. **把 `sessionEvents()` 一起迁移到 `sessionProjections.register()`**：否决（本轮）。同 `implemented/architecture/2026-09-17-synchronous-session-history-waiver.md`：0.1.7 仍然保留 `snapshotEvents()`，替代品 `page()` 拿不到工具证据，迁移触发条件未到。
8. **删掉直连 logprobs 通道、只保留显式标签**：否决。直连通道是"优先概率期望评分"的全部实现，删掉等于把评分从分布期望退化成单次采样字母；代价远大于维护一个 12 行的接缝探测。
9. **继续调 `settings.get(ns)` 并用可选链吞掉异常**：否决。`SettingsForms` 上 `get` 是 `undefined` 而非"读不到"，可选链会把 0.1.7 上**所有**直连通道静默降级——看起来没崩，但概率期望评分在 0.1.7 上永久失效且没有任何信号。改成显式探测 `get` → `describe()` 才能真的读回配置。

## Consequences

- **宿主面**：0.1.1–0.1.7 的会话事件仍走同一套读取；工具结果的成败与内容在两侧宿主上都能取到。`session.test.ts` 新增的三条回归用例分别钉住消息级标志、嵌套块的 `undefined` / 空数组边界，以及"旧宿主嵌套输出仍渲染成 `[Tool Result]` 证据"这条端到端路径（用真实 `Session` 追加一条 0.1.6 形态的 `tool/result` 事件）。
- **注入身份**：插件的 steer/反馈文本在 0.1.7 上显示为 `llm-verifier` 的注入行；迁移过的历史行显示为 `plugin:dsh-llm-verifier`。两者都不参与判定。
- **验证基线**：`pnpm run verify:release`（`typecheck` 锁定 `0.1.7-alpha.1` + 全部单测 + 重建 `lib/`）通过；测试侧另有一批迁移：168 处 `session.events` 改成 `session.snapshotEvents()`（`Session.events` 早已不存在，这些测试此前实际跑在 0.1.1 的宿主类型上）。
- **已收窄的能力**：客户端面的类型基线随 `devDependencies` 一起落到 0.1.7。图标探测让旧宿主**不白屏**，但 `client.tsx` 的其余部分只在 0.1.7 类型下被检查；若日后要重新锁回最低基线验证客户端面，需要先把图标以外的差异也做成分支读取。
- **遗留债**：`tsconfig.local.json` 仍以 `../deepseek-harness` 为约定路径（本机不满足），本轮只补上新增的 `@deepseek-ai/dsh-client-ui-renderer/client` 映射，未改变该约定。
- **设置读取**：`llm-deepseek` / `llm-pi-ai` 的配置在 0.1.1–0.1.7 全线上都能读到——旧宿主走 `get(ns)`，0.1.7 走 `describe()` 的 `value`。任一接缝缺失、抛错或答非所读时 `settingsNamespace()` 返回 `undefined`，路由解析据此判定"没有直连通道"并降级到显式标签，绝不把设置层异常抛进验收。`top-logprobs.test.ts` 的四条回归用例分别钉住两代接缝、不可用接缝的降级（含 `describe` 抛错）以及描述符筛选与 `api: openai-completions` 白名单。
- **维护入口**：本次升级的流程、跨版本陷阱与要点索引已收进 `.agents/skills/dsh-version-upgrade/SKILL.md`（见 `implemented/process/2026-09-22-dsh-version-upgrade-skill.md`），下一次宿主更新从那里开始。
