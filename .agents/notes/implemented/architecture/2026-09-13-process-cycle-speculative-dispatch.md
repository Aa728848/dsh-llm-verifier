# Agent Note: 过程选优的购买与生成改为与原回复并发（投机执行）

Status: implemented

## Problem

过程选优的新增延迟一直是它最大的产品阻力：`handle()` 必须先把整条原回复缓冲完，**之后**才读策略、预约、写购买记录并派发生成，最后比较。用户等待的是三段时间之和（原回复 + 生成 + 比较），而 `caller.ts` 的实测是会话模型一份草稿就能花掉约 8k 推理 token——生成这一段往往是几十秒级。

而「这次请求可能要选优」在请求派发**之前**就已经确定：意图是 `agent/pre-step` 登记的，`take()` 也已经在 `llm/stream` 上把它绑定到这次主请求。也就是说，进入 `handle()` 时唯一缺的信息是**原回复长什么样**，而备选生成并不需要它（备选请求的消息与原请求逐字相同）。

## Decision

`handle()` 在缓冲原回复**之前**就调用新的私有方法 `beginCycle()`，并把返回的 `StartedCycle` 与缓冲过程并发：

- `beginCycle()` 依次做：live/信号/任务检查 → `policy()` → `reserve()` → `store.begin()` → 购买后的 stale 检查 → 派发 `drainAlternative(ctx.llm.stream(request))`。**顺序不变量保持不变**：任何新增模型调用之前，预约与购买记录都已经完成；写不进购买记录仍然直接 `fail` 且不买。
- 阶段截止时间、父信号链接与 `cycles` 注册都移进 `beginCycle()`，`StartedCycle.cleanup()` 是**幂等**的（清定时器、摘监听、注销在途周期），因此失败分支与 `handle()` 的 `finally` 都调用它也不会重复动作。
- 派发的 promise 立刻挂一个空 `catch`，保证被丢弃的周期不会变成未处理拒绝；真正等待它的路径仍然能看到拒绝。
- 新增 `abandon(cycle, ...)` 统一处理「丢弃并回放原回复」：**已购买**的周期 `fail` 预约、abort 阶段、用 `settledUsage()` 结算已经报出的用量，并写一条 `purchased: true` + `generatedCalls: 1` 的行；**未购买**（`beginCycle` 返回 undefined）的周期**不写第二行**——它已经为这次请求写过一条「为什么没买」的行，再写一条会把跳过分布灌水。
- 因此原回复超限（1 MiB）、finish 不合法、内容为空、以及流式中途关闭开关/取消/换任务这些**稀有分支**，从「不买就跳过」变成「买到一次生成再作废」。这是**如实计数**（派发确实发生了），代价也第一次写进 README 与 AGENTS.md。
- 阶段截止时间从周期开始计，所以它现在覆盖整个重叠窗口：极慢的原回复可能吃掉备选的时间预算。这是有意的（一次周期的总时长因此有界），但语义与之前不同，已在文档中写明。

验证基线：`pnpm run typecheck` 与全量测试通过（581 条）。`process-selection.test.ts` 新增一条断言「原回复 finish 之前备选已经派发」（用桩 store，避免把文件写入延迟当成被测对象），并把超限/不完整两条用例改成断言新语义（`purchased: true`、`generatedCalls: 1`、`reserved`/`failed` 各 1）；`index.test.ts` 走真实钩子的整条链路不受影响。

## Alternatives considered

1. **保持顺序执行，只把裁判调用并行化。** 不采用。比较本来就已经并行（`engine.compare` 的 job 是 criterion × repeat 并行发射），真正的串行大头是生成，不解决生成就等于没解决延迟。
2. **先并发生成，等原回复完成后再补预约与购买记录。** 不采用。那会让「先买后调」这条不变量失效：购买记录写不进去时，生成已经花掉了。宁可多付稀有分支的一次生成，也不放松记账。
3. **只对「原回复已经流了一部分」的请求投机（例如超过 N 个 chunk 再启动）。** 暂不采用。它把延迟收益系在一个新的启发式上，而且判断本身要等原回复——省下的恰是启动等待。等真实对照数据表明「稀有分支的浪费」不可接受时再加也不迟。
4. **把 `generated` 的拒绝吞掉，只在成功时结算。** 不采用。生成失败与取消正是最需要保留已发生用量的两种情形，`settledUsage()` 在失败出口用调用方持有的 chunk 数组补 `usageIncomplete`。
5. **给未购买的周期也补一条 `abandon` 行。** 不采用。同一次请求会出现两条跳过行，`bySkipReason` 与 P05 的触发/跳过分布都会被灌水，而 P05 正是要读这些数。

## Consequences

- 新增等待从「原回复 + 生成 + 比较」降到「max(原回复, 生成) + 比较」；在生成比原回复慢的常见情形下，等于砍掉一整轮生成的等待。
- 稀有分支多付一次生成，并且这条代价第一次有了明确的记录与文档；它是否值得由 P05 的对照数据判断（`route.generatedCalls` / `outcome` 现在能直接读出这些行）。
- `handle()` 的早期分支不再自己写行，全部走 `abandon()`：一个匹配到意图的请求**恰好产生一条**统计行。
- 阶段超时语义变化（覆盖重叠窗口）已写进 README 与 AGENTS.md，避免后来者把它当成 bug。
