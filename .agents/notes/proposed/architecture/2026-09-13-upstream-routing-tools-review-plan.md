## Decision

### 1. 总体判断

**架构方向符合 DSH 插件的定位，但尚不能认定所有模式和工具都达到声明的预期。应先修验收契约与宿主接线，再做算法差异评测和参数校准；不需要重写路由器，也不应照搬全请求代理。**

五工具分工、结构化优先、语义引用分类、停止前最终验收、逐项阈值和有限 steering 都有合理依据。问题主要出在连接这些部件的边界：真实输出字段、被评审的会话区间、宿主返回包装、失败证据、预算预留与去重范围。现有单元测试通过，尚未覆盖这些完整连接。

对照中值得保留的实现已经存在，不应再次排期为新功能：

- A–T 标尺、Bradley–Terry 软胜率、PPT 主流程，以及按判据和轮次评分。
- 前缀预热、确定性证据分隔符、运行时探测评分通道、显式标签降级。
- 相同候选短路、重复候选去重、评分缓存和 in-flight 合并。
- 独立的路由/最终验收尝试计数，`track` 达标后的 `preferFinal`。
- 默认判据、自定义判据失败退回 coding、判官自检、统计、决策快照和离线阈值回放。
- `verifier_best_of_n` 的生成、锦标赛、胜者对空工作基线的额外验收。

### 2. 三方实现的对应关系

| 维度 | Python 上游 | TurboAgent | 本项目及评价 |
| --- | --- | --- | --- |
| 接入层 | `compare/select/track/ProgressTracker` 库接口 | Anthropic/OpenAI 兼容请求代理 | DSH 工具与生命周期钩子；适合利用真实执行证据 |
| 候选来源 | 调用方提供轨迹 | 每次模型请求并发生成回复，包含待执行工具调用的文本表示 | 已有候选走 compare/select；best-of-N 仅显式生成文本。三者不可当成相同实验 |
| 选择后执行 | 由调用方负责 | 返回胜者响应，由客户端继续执行 | 自动路由 steering 要求主 Agent 实施胜者；最终验收检查执行结果 |
| 进度 | 批量离线 track；另有只看前缀的在线 ProgressTracker | 选定回复后的后台观测，不改变所选回复 | track 参与 steering，但不代替最终验收；应保留这一边界 |
| 失败处理 | 分数解析失败可回落 0.5；select 默认 `on_error="tie"` | 判官失败时可以返回首个候选；多数相同也可跳过判官 | 本项目解析报错更适合门控，不能为“对齐上游”改成静默通过 |
| 生成成本 | 不负责起草 | 每次被代理的生成请求承担 N 份生成和选择成本 | 显式 best-of-N 可控，自动路由不生成候选的设计应保留 |
| 诊断 | 缓存与调用统计 | 每请求流程、候选、比较记录与进度可视化 | 已有统计/快照；后续重点是解释未执行、未验收和降级状态 |

### 3. 模式和工具是否达到预期

#### 自动模式与附加门控

| 模式/阶段 | 代码中的实际语义 | 评价 |
| --- | --- | --- |
| manual | 关闭自动停止门控与计划预审，保留显式工具；工具描述仍允许 Agent 自主选择调用 | 符合“仅显式工具路径”，不等于每次必须由用户手动点名 |
| smart | 结构化路由优先；有 Subagent/Workflow/计划产物线索时分类；通常需有实质操作和至少 3 次工具调用才最终验收；自动路线成功可强制最终验收 | 方向合理，但 F01–F06 使覆盖范围和闭环不完全可靠 |
| strict | 每个可进入的停止边界尝试分类；一次完成的实质操作即可触发最终验收；异常时有限 steering | 属于预算内严格复核。预算耗尽后允许退出是现有明确取舍，不是不可绕过的完成证明；应呈现“未验收”状态 |
| 计划预审 | 主判官的一次文本判决，低分拒绝计划；异常、无判决或预算不可用时让计划继续到人类审批 | 人类审批前的辅助诊断，异常放行应保留；不应宣称与最终逐项、多裁判验收同等强度 |
| Team 任务闸 | 在停止边界逐个检查已完成任务，用主判官文本判决，消耗路由次数 | 功能存在，但团队任务问题提取有缺口；批次超过预算时并不保证每项都已复核 |

对应：[index.ts](../../../../src/index.ts) 578–839、[auto.ts](../../../../src/auto.ts) 125–183、[router.ts](../../../../src/router.ts) 633–942。

smart 的“智能”目前是高置信分类加启发式门槛，并非经标注数据校准的路由策略。`confidence >= 0.9` 是模型自报数值，不能解释为 90% 的正确率。纯阅读、检索、分析或直接输出文本的任务可能不满足“实质工具操作”条件；配置 research/writing 判据也不会自动改变这一触发条件。暂不扩大默认触发范围，先在 F09 中测量漏检与额外成本。

#### 五个显式工具

| 工具 | 已达到的部分 | 尚需处理或明确的限制 |
| --- | --- | --- |
| verifier_compare | 两候选逐项评分、位置交换、通道降级、逐裁判结果、相同候选返回中性 tie | 显式调用允许奇数 repeats；质量接近时差值不足以证明优劣。需把调用上限和判据输入检查与其它工具统一 |
| verifier_select | 已有候选 PPT、去重与稳定排名；不把相对胜率直接当验收分 | F07：自定义 pivots 和裁判数没有完整进入调用上限检查。F08：实际赛制不与上游逐位等价 |
| verifier_track | 显式检查点、重复平均、多裁判；自动路径只依据最新检查点决定下一步 | F06：失败的真实工具结果被证据索引丢弃。离线曲线仍不能当在线无未来信息的评测结果 |
| verifier_current_session | 读取真实会话、脱敏、基线比较、逐项阈值结果 | F01：真实结果回读字段错误，旧区间验收也可能解除当前门控；F04：纯团队消息窗口缺少 problem |
| verifier_best_of_n | 当前会话模型起草 N 份，幸存至少 2 份，选择后保留绝对验收，报告失败与截断 | 生成的是静态文本，不会执行草稿中的代码和测试；对 coding 判据，缺少实际验证输出可能使候选均不达标，这是如实报告证据不足 |

`select.scores` 是对局偏好份额，`current_session.score` 和 best-of-N 的单数 `score` 才是验收口径；两者不能共用阈值。即使 best-of-N 文本被评为可接受，也不能解除后续落盘、执行后的会话门控。其现有基线比较必须保留。

对应：[engine.ts](../../../../src/engine.ts) 222–699、[index.ts](../../../../src/index.ts) 281–415、842–899、[历史 best-of-N 验收记录](../../implemented/feature/2026-09-13-best-of-n-generation-side-selection.md)。

### 4. 已确认问题与改进项

以下 P0 表示应在下一次将门控视作可靠保障之前修复；P1 表示紧接着处理的功能正确性或成本约束；P2 表示有数据后再调整的行为。优先级不代表本次已经发生生产事故。

#### F01 · P0：显式会话验收的回读契约会漏掉失败判据

**证据与复现**

- `verifySession` 实际返回 `criteria: [{id, name, score}]`，见 [index.ts](../../../../src/index.ts) 281–288。
- `parseSessionVerdict` 却只读取 `item.scoreA`，见 [auto.ts](../../../../src/auto.ts) 83–98，实际返回中的判据因此全部被过滤。
- 用 `score=2/3, winner=A, criteria=[1,1,0]` 的真实字段形状回读：`sessionAccepted` 返回 false，而 `analyzeAutoTask` 返回 `manualVerificationAccepted=true, reason=already-verified`。入库 `lib/index.js` 也复现。
- [auto.test.ts](../../../../src/auto.test.ts) 96–102 的 fixture 使用了 `scoreA`，所以现有测试没有暴露错位。
- 另一个独立缺口：返回 `toSeq=2` 的旧区间通过判决，在任务已工作到 seq 6、工具回执到 seq 8 时，仍被视作当前验收。回读未核验覆盖区间，`stale()` 以回执时点而不是被评审区间判断新旧。
- 自动路线已设置 `finalRequiredFromSeq` 时，显式通过只影响 `evidence.eligible`；停止钩子仍可因 forced 标记再次验收。该项为调用链静态确认，尚未单独运行钩子复现。

**最小方案**

读取当前真实 `score` 字段；当前工具返回的缺失、非法或被过滤后的判据不得默认为“全部通过”。核对会话身份、任务窗口和 `fromSeq/toSeq`，以实际覆盖的最后工作结果判断是否过期。只有覆盖当前要求的有效通过结果才能清除 forced 标记，并应在再次购买路由前处理。

保留旧统计文件的宽松读取规则；历史统计兼容性不能成为当前门控接受不完整判决的理由。不默认给评分接口增加另一套阈值。

**验收**

在 `index.test.ts` 的现有装配 seam 中，将注册工具的真实返回值经过 renderer/事件回读后再判断门控。覆盖逐项 0 分、恰好等于阈值、缺失判据、旧 `toSeq`、验收期间完成的操作、通过后新增编辑、通过后的强制标记解除。成功调用次数只应在真正需要复核时增加。

#### F02 · P0：语义分类的输入边界没有闭合

**证据与复现**

[router.ts](../../../../src/router.ts) 694–731 对 artifacts 做了单项脱敏，但 Todo 快照直接 `JSON.stringify(todos)`。首个快照即使超过剩余预算也会被加入；任务、元数据及序列化膨胀没有统一计量；此提示词也没有复用 `renderDelimitedBlock/evidenceNonce`。

用合成的 `api_key=sk-...` 和一万字符 Todo，设置单项 100、总量 1000：构造出的提示词长 10877，仍含合成密钥，且没有确定性分隔块。此为本地构造结果，未向外部模型发送该输入。

引用也未限制到实际呈现的集合：三个合法产物中一个被提示词预算省略后，`semanticDecision` 仍接受分类器对该产物 ID 的引用。它查的是完整会话索引，而非此次分类可见列表。不存在的引用目前会记录 `invalid-references`，但随后仍 commit 分类预约；严格模式没有把这种引用错误当作失败，见 [index.ts](../../../../src/index.ts) 707–720。

**最小方案**

为这一路径构建一个小型“已脱敏、已限长、可见引用集合”结果，直接供提示词渲染和引用校验共用。所有 Todo 内容和文本字段先脱敏，按 `itemBudget()` 分配证据预算，计入 JSON 包装成本；静态提示词开销另行明确。任务、产物、检查点使用既有确定性分隔块，保持 JSON 输出严格校验。

严格拒绝未展示的引用；`none`、低置信分类与非法引用必须有不同的结果状态。strict 中非法引用走失败路径并消耗已有预算，不无限重试。

**验收**

合成密钥不出现在最终提示词；单个超长 Todo、多个短 Todo、长 ID、引号和换行的序列化均有界；上限恰好相等时可执行；被省略 ID、未知 ID、协调工具 ID、伪结束符都不能越过边界。同一输入生成相同提示词前缀。

#### F03 · P1：结构化 Workflow 候选协议与当前宿主返回不匹配

**证据与复现**

本地 DSH 的 `tool-workflow/src/index.ts` 195–201、256–268、310–314 返回 `{runId, agentsStarted, result}`，随后渲染为前导说明加 `Return value:\n<JSON>`。

本项目在 [router.ts](../../../../src/router.ts) 639–640 对整段工具文本做 `strictJson`，而候选 envelope 必须位于 JSON 顶层。把合规的 `dsh-verifier-candidates` envelope 放进宿主实际渲染格式后，结构化路由返回 undefined。现有测试输入则是没有宿主包装的裸 JSON。

这证明该本地宿主形态的结构化快路径不可达；并不证明所有宿主版本都失败，也不表示语义回退永远无法选候选。

**最小方案**

先确认两个受支持宿主版本是否有可读取的结构化工具结果；优先从该接口取得 `result`。若只有渲染文本，只对已确认的 Workflow 包装作严格、有限的解包，不从任意工具文本中宽松搜寻花括号。

继续要求版本、组 ID、完成状态和非空候选；被宿主截断的 JSON 拒绝。README 给出能由实际 Workflow 执行并返回的最小 envelope 示例。保持一般 Subagent 结果必须语义判断的规则。

**验收**

对 npm 锁定宿主和本地 0.1.5 形态分别提供真实 renderer/事件 fixture；合法同组候选进入结构化 compare/select，额外说明、半截 JSON、失败子任务和不同子任务不能变成受信候选。已知协议路径无需一次语义模型调用。

#### F04 · P1：团队消息被识别为任务边界，却不能成为验收问题

**证据与复现**

`latestDirectUserSeq` 已接受 `team-message`；[session.ts](../../../../src/session.ts) 101–108 却只在 `sourceKind === 'user'` 时设置 problem。仅含团队任务消息的窗口可生成非空 trace，但返回 `problem=""`；`verifySession` 随后在 [index.ts](../../../../src/index.ts) 283 抛错。

本地 DSH `packages/experimental/agent-team/src/mailbox.ts` 242–250 确实生产 `team-message` 来源消息。实际影响取决于该会话是否被配置进入门控，以及提取窗口中是否还保留普通用户任务。

**最小方案与验收**

让任务问题提取与既有边界定义一致，使用该窗口真实的任务来源；不把插件 steering 当新任务。覆盖仅团队消息、普通用户后转交、团队新任务重置、缺少任何任务四种形状。最终验收能读到被指派任务，而不是空字符串或上一个任务。保留默认不门控普通子 Agent 的配置。

#### F05 · P1：旧候选和工具种类去重会遮住尚未评审的新对象

**证据与复现**

[router.ts](../../../../src/router.ts) 643–646 每次先选候选数最多的组；是否已处理在选完之后才由 reserve 判定。[index.ts](../../../../src/index.ts) 737–751 被拒绝后不会继续找下一组或 track。

内存复现：先有 4 候选旧组，再加入 3 候选新组，分析仍返回旧组及完全相同的 fingerprint。若旧组已执行，新组不会通过这次结构化路线被处理。

此外，`successfulExplicitKinds` 按整个任务中是否出现过某类 verifier 工具抑制结构化路由，而非按本次输入是否相同。一次显式 select 之后，新的候选组也被屏蔽。当前 README 描述了这种大范围抑制，需要同时修订契约。反过来，语义决策未复用同一对象去重，可能又评一次已显式处理的对象。

**最小方案**

在保持 select → compare → track 优先级的前提下，从未处理的对象中选路由；成功评审凭据绑定任务、对象指纹和证据版本。只跳过同一份输入，不用一个工具名屏蔽整个后续任务。

不要增加通用工作流调度器。针对当前三类 RouteDecision，收紧选择与去重的连接即可。候选胜者反馈应带可定位的组/候选/调用 ID，避免多个同名标签使 Agent 无法找到胜者。

**验收**

旧组已评审、新组可进入；显式 select 后旧组跳过、新组保留；没有新证据时零重复评分；旧 select 不挡住新的 track；语义与结构化路径对同一对象共享去重语义。

#### F06 · P1：track 只收集成功结果，会漏掉最新失败证据

**证据与复现**

[router.ts](../../../../src/router.ts) 193–225 在建索引时排除了错误 `tool/result` 和失败 PTC dispatch，最新验证摘要也只能在这份索引里寻找证据。

内存复现：先有 `Tests 12 passed`，后来同一类命令返回 `isError=true` 的 `FAIL 1 test failed`，再更新 Todo。最新 track 检查点包含旧通过输出，却不包含新失败。带文本但宿主未标记 isError 的失败不会被这个分支排除；问题指向明确标记失败的结果。

最终会话提取仍保留工具结果，因此这不是“所有最终验收必然通过”的证明；它会误导中途进度并改变后续调度。

**最小方案与验收**

区分“可供选择的成功候选”和“描述执行状态的真实观测”。候选必须成功，检查点必须能看见失败。扩展现有证据索引携带结果状态，继续共用协调工具排除规则及预算分摊。

先通过后失败必须展示最新失败，并标明旧验证的时间关系；修复后重新成功应恢复为最新证据；普通工具和两种 PTC 事件均覆盖。不要让失败产物进入 select，也不要把 verifier 自己的分数重新当工作证据。

#### F07 · P1：调用预算尚不能保证最终验收或显式上限

**证据与复现**

1. **最终验收没有模型调用额度预留。** [router.ts](../../../../src/router.ts) 850–874 虽分开尝试次数，仍直接扣同一个任务/会话模型调用余额。使用默认任务上限 96，7 候选、3 判据、1 轮、2 裁判的路线预约为 90；后续最终验收需要 12，却被拒绝。该配置合法，且路线已经能设置强制最终验收标记。smart 的最终预约失败分支直接 return，见 [index.ts](../../../../src/index.ts) 812–820。

2. **显式 select 上限检查忽略自定义 pivots 和裁判倍数。** [index.ts](../../../../src/index.ts) 105、844 用固定两 pivot 的估计值检查 500 次限制。16 候选、16 pivots、3 判据、2 轮，检查值为 252；真实引擎 scripted stream 跑出 120 场、720 次调用。此例仅一个裁判，已超过声明上限。

3. **预约与实际消费不是同一指标。** 预约按预计逻辑评分数增加，未按缓存命中结算；调用重试另有 attempts/retries。总失败分支还把统计写成 `emptyRunStats()`，见 [index.ts](../../../../src/index.ts) 248–251。不能用当前 calls 汇总声称掌握所有实际网络尝试和失败成本。

**最小方案**

路由入场时为至少一次最终验收保留任务与会话两层额度；以当前判据数、最终 repeats 和裁判数计算。总预算不足以覆盖最小验收时，提前呈现明确原因。保留已分开的尝试计数和一次性耗尽提示。

显式 select 按实际 N、K、repeats、判据数、裁判数计算安全上界，必要时在 ring 得出 pivots 后对第二阶段做精确检查；在发生模型请求之前拒绝确定超限的输入。compare/current_session 的自定义判据与调用数量边界一并核对，不引入第三套计费语义。

将“预约逻辑调用数”“已完成评分调用数”“网络尝试/重试”分清；不得把未知失败 token 伪造为已知 0。取消、缓存命中和部分失败是否返还预约，应在同一预算实现里明确，并确保不透支、不中途放开并发预约。

**验收**

90 + 12 的例子应在路由入场时被限制或调整，不能先承诺强制验收再无钱执行；任务预算、会话预算都覆盖。显式 720 次例子必须在首个请求前拒绝；500 边界与多裁判倍数有测试。重复缓存、取消和失败不会凭空制造额度。预算耗尽必须能在看板或任务记录中看到“未验收”，同时无 steering 活锁。

#### F08 · P1：算法差异说明与 parity 覆盖需要纠正

**已经确认的差异**

- 同字母 token 变体：本项目求和，上游取 max。这一差异已明确记录，应保留。
- PPT：上游最后把 ring 和完整 pivot pairs 都累积；本项目按无向边删掉与 ring 重合的 pivot 边。它不仅减少请求，还改变 wins/counts 权重。
- 相同 seed 不保证相同 ring：上游 `random.Random(seed)`，本项目自带 `seededRandom`。
- 解析失败、重复候选、两候选赛制、温度、K=1 位置定向和宿主门控均有本地选择，不能纳入“只有一处实现差异”的笼统声明。
- 上游 K≥2 会交替 A/B；不能再次把它描述成所有配置都有未修正的位置偏差。本地 K=1 的定向减少偏差也不等于实测排名质量已得到保证。

**无模型数值复现**

固定相同 ring 为 `[(3,2),(2,0),(0,1),(1,3)]`，第一阶段得到 pivots `[3,2]`；固定下表每对分数，反向比较交换分数，因而没有位置偏差：

| 候选对 | 左侧/右侧 reward |
| --- | --- |
| 0,1 | 0.75 / 0.25 |
| 0,2 | 0.25 / 0.75 |
| 0,3 | 0.75 / 0.25 |
| 1,2 | 0.75 / 0.25 |
| 1,3 | 0 / 1 |
| 2,3 | 0.5 / 0.5 |

按上游 ring + 完整 pivot 计权，胜者是 **3**，得分约 0.567932；按本项目去重计权，胜者是 **0**，得分约 0.540820。两边均非最高分平局。此复现仅隔离聚合语义，不代表哪种赛制在真实任务上更准。

来源：[上游聚合](https://github.com/llm-as-a-verifier/llm-as-a-verifier/blob/8db8a114355a9d7fdf9a8d1d5c87f6aeebd18770/llm_verifier/__init__.py#L212)、[PPT 公式](https://github.com/llm-as-a-verifier/llm-as-a-verifier/blob/8db8a114355a9d7fdf9a8d1d5c87f6aeebd18770/llm_verifier/pivot_tournament.py#L38)、[上游换位](https://github.com/llm-as-a-verifier/llm-as-a-verifier/blob/8db8a114355a9d7fdf9a8d1d5c87f6aeebd18770/llm_verifier/fine_grained_reward.py#L843)、[本项目 engine.ts](../../../../src/engine.ts) 640–657、[core.ts](../../../../src/core.ts) 366–420、[parity.test.ts](../../../../src/parity.test.ts)。

**最小方案与验收**

先将文档改成“共享算法基础与明确列出的本地变体”，分别列出评分、赛制、运行策略的契约。保留现有去重行为，暂不回滚。

加入固定 ring、固定 reward 的离线聚合 fixture；上游一致项必须一致，刻意差异必须有各自期望值。CI 使用锁定上游提交导出的最小黄金数据，不再把同级 checkout 的可选存在当作主要一致性保障。上游 Python 实跑仍可作为补充。

若后续比较“上游加权”和“本地去重”哪种更好，先复用固定配对分数隔离赛制影响，再在有标签任务上比较质量与调用成本。只有新数据支持才改算法；评分语义变化遵守缓存 version 规则。

#### F09 · P2：补足路由效果、判别能力和诊断记录的证据

**现状**

离线 replay 已能扫描阈值，但没有任务真实通过/失败标签，仅凭通过率曲线无法得出最佳阈值。[replay.ts](../../../../src/replay.ts) 现有能力应复用，不另造一个评价平台。

历史 best-of-N Note 记录 explicit-tag 难分候选的 gap 约 0.018；本次未重测。该现象支持限制使用范围，不支持把固定 gap 当通用置信区间。`agreement` 也只是裁判胜负一致比例，不是校准后的可信概率。

计划预审与 Team 闸目前只用主裁判和固定技术类提示词；track 不使用 configuredCriteria；多判官逐项中位数不保证每个任务都获得一套完整、同样规模的评分。应先明确这些语义，再决定是否扩展配置。

统计已有跳过原因的一部分，但一般预约拒绝、低置信/none、耗尽未验收、失败过程中的实际调用和快照仍不完整。TurboAgent 的请求过程可视化可借鉴其“解释发生了什么”，不必复制整套 DAG 前端。

**小范围计划**

1. 建立首批约 30 个脱敏、人工标注的任务样本，分层覆盖代码修复、只读分析、已有候选、Todo 长任务、团队转交、失败/取消和纯对话。它用于发现问题，不作为低误放行率的统计证明。
2. 固定模型、通道、判据与版本，分别比较 manual、smart、strict；记录应路由/实际路由、错把子任务当候选、漏掉关键验收、重复调用、未验收退出、额外请求和 P50/P95 延迟。人工判定要依据产物和验证结果，不能使用判官自己的分数作标签。
3. 候选选择分开评测明显优劣和质量接近两组，记录选择正确率、平局比例、位置互换稳定性及成本。对 explicit-tag 与 top-logprobs 分组报告，不套用上游 benchmark 的提升幅度。
4. 对有真实标签的最终验收报告误放行、误阻断和缺证据率，再决定是否调整 0.65、0.684、0.9 及重复轮数；样本不足时报告原始计数与不确定性，保持默认值。
5. 给现有 verdict/统计补充必要的可选状态，明确 accepted、rejected、unverified、skipped 原因及裁判降级；旧记录照常读取。`success` 继续表示调用是否抛错，不改成验收结果。
6. best-of-N 的反馈区分“草稿需要执行验证”和“验证运行已失败”，继续保留基线及 `passesThreshold`。下一步是实施和测试胜者，再做 current_session；不自动补造执行证据，不静默换用更松判据。

## Alternatives considered

1. **全面复制 TurboAgent，在每次模型请求前生成并筛选 N 份回复。** 不采用。它改变本项目的接入层和成本模型，且在候选工具调用尚未执行时只能评估潜在效果；现有 DSH 停止边界能取得真实证据。已有显式 best-of-N 足以承接当前生成侧需求。

2. **为了逐位 parity 恢复上游所有行为。** 不采用。上游解析回落中性分、选择失败返回替代结果等行为不适合作为验收门控；重复边计权是否更好仍需评测。先准确记录差异，再决定必要变化。

3. **先降低阈值、增加自动路由次数或默认增加裁判。** 不采用。字段错位、被丢掉的失败证据和预算预留问题不会因此消失；增加裁判还会放大 F07 的调用预算缺口。

4. **先做在线 ProgressTracker、自动提示词改写或重建 DAG 看板。** 暂缓。当前并没有充分证据说明这些新增机制比修复已确认的连接问题更有效。保留离线 track 对最新状态的使用，不把全曲线当在线估计。

5. **只补 README，依据现有测试全绿认定功能达标。** 不采用。F01、F02、F04、F06、F07 已有运行复现；F03 有真实宿主源码与包装复现。它们需要代码回归，文档无法替代。

6. **重新在 docs/ 维护一套评审文档。** 不采用。按仓库现有约定，本评审和后续计划统一放在 proposed Agent Note；避免与已迁移的历史决策记录重复。

## Consequences

本次形成了带固定版本、源代码位置、复现结果、分级计划和验收标准的单份 Markdown 提议。未改 `src/`、`lib/`、README 或运行配置，未提交或发布，也未进行真实模型调用；因此没有重建产物或执行发布门禁。

执行该计划后，首先改善的是“需要验收时确实验收、失败证据确实可见、工具返回确实被正确理解”。模型评分能否提升真实交付质量仍要由分层评测回答，不能用类型检查、单元测试或上游 benchmark 代替。

当前应保留的产品边界：智能路由是辅助调度，最终验收才是交付判断；严格模式受有限预算约束；计划预审仍交由人类最终批准；best-of-N 保持显式调用和不可省略的基线比较。
